%%ABSTRACT:
JSON parsing sits on the hot path of many Node.js servers, and the default runtime strategy fully materializes every incoming document before the first field is read. This article evaluates on-demand parsing as that alternative: a C++23 JSON parser exposed through a WebAssembly 64-bit binding, which materializes only the document regions an application actually reads. We compare it against the V8 JSON.parse baseline on a real Node.js state-store workload across five boundaries — full materialization, partial projection, selective traversal, repository access, and a complete HTTP endpoint — on two sites: a development device and a production-like server. Every cell rests on 15 paired measurement rounds and a locked estimand, S = T_V8/T_ZE computed as the ratio of round-level medians, with 95% paired-bootstrap confidence intervals (B = 10,000). Under full materialization the on-demand path is 15–23× slower than V8 (S = 0.04–0.07); under partial projection it is 6–13× slower (S = 0.08–0.16); under selective traversal the comparison becomes payload-dependent (S = 0.05–1.65, crossing 1 for some documents). A warmed canonical-bytes repository is 2.88× (2.67× on the server) faster for the on-demand configuration, whereas the file-store path shows no advantage. At the HTTP endpoint the advantage is not distinguishable on the dev device (S = 1.05/1.03) and modest on the server (S = 1.15). These boundary-resolved results show a wasm on-demand parser can win where the store design avoids re-parsing but loses to V8 under full materialization; the published protocol supports reproducible evaluation across those boundaries.

# INTRODUCTION

The JavaScript Object Notation (JSON) is the default data-interchange format of modern web services [1], and on servers that accept, store, and serve JSON payloads, parsing executes on nearly every request. Node.js is one of the most widely deployed platforms for such servers, and its JSON strategy is inherited directly from the V8 engine: JSON.parse validates the entire document and materializes it into an object graph before the application can inspect its first field. The cost of this eager strategy is therefore paid in full on every request, regardless of how little of the document the request actually needs [2]. Because the materialization happens inside the engine, the application can also incur allocation, property-creation, and garbage-collection costs for content it never reads — a general property of eager parsing that this latency-only protocol does not measure.

On-demand parsing inverts that contract. Instead of building a full document object model, an on-demand parser locates the requested value directly in the raw bytes and materializes only what is read; the interface to the programmer still resembles a conventional DOM, while the underlying implementation is a pointer walk through the content [2]. The strategy was popularized by simdjson, which parses gigabytes of JSON per second on commodity CPUs [3], and it has since been adopted by production systems, including the Node.js runtime itself [2]. The distinction matters economically for store-shaped workloads — documents read far more often than they are rewritten — because the on-demand contract turns parsing cost from a property of the whole document into a property of the access pattern, which is exactly the quantity a server workload can control [2].

A second line of work reduces parsing work to what a query needs. Mison couples a structural index with projection pushdown so that only queried fields are decoded [4]. Sparser filters raw bytes before any parsing happens [5]. JSONSki fast-forwards over uninteresting regions of semi-structured data [6], and JPStream compiles query and parsing stages jointly [7]. Pison scales structural-index construction [8]. Within the JavaScript ecosystem itself, FAD.js applies JIT-based speculative optimizations to accelerate selective JSON access inside the engine [9]. Beyond in-process servers, JSON Tiles automatically detects the most important keys and extracts them transparently, achieving scan performance similar to columnar storage [10], GpJSON moves JSON processing onto GPUs [11], descendant-aware JSONPath engines extend selective access over deep paths [12], and streaming validators check documents against schemas without materializing them [13].

Selective and on-demand parsers in turn rely on production-grade primitives for the scalar stages of text processing: number parsing at a gigabyte per second [14], UTF-8 validation at less than one instruction per byte [15], millions of URLs [16] and DNS records [17] parsed per second, AVX-512 unicode transcoding [18], transcoding of billions of characters per second [19], Base64 codecs at memory-copy speed [20], SIMD repair of ill-formed UTF-16 [21], and forgiving Base64 error handling [22]. Several of these primitives are integrated in V8 and Node.js, so they form a demanding baseline against which any replacement parsing strategy must be measured.

WebAssembly offers a delivery mechanism for native parsing code inside a JavaScript application without engine modifications. The performance of WebAssembly applications, however, depends strongly on the runtime environment and can deviate from native execution [23]. An empirical study of 510 NPM packages documents WebAssembly usage in the Node.js ecosystem [24], the runtime landscape has been surveyed in [25], and benchmarking studies document interpreter and JIT overheads on constrained targets [26] as well as server-side WebAssembly runtime deployments [27]. Compiling a native parser to a portable binary and invoking it through a small C ABI is therefore a realistic engineering path for Node.js servers — but whether its laboratory advantages survive a real server's boundaries is an empirical question.

Existing evaluations of on-demand and selective parsing largely measure a single boundary: an isolated parse loop, a projection micro-benchmark, or an analytics query. A server, however, interposes more boundaries between the parser and the user-visible response: partial projections over stored documents, repository layers that cache and reshape bytes, and the HTTP stack itself. A speedup measured at one boundary does not imply a speedup at another, and performance-reporting discipline demands explicit estimands, paired designs, and confidence intervals rather than single-number summaries [28]. Why a multi-boundary evaluation rather than a parser micro-benchmark? Because each layer between the parser and the user can amplify, preserve, or erase a parsing advantage: a projection layer changes how much of each document is touched, a repository layer decides whether bytes are re-parsed per request or transformed once and cached, and the HTTP stack adds fixed per-request work that no parser can shrink. A speedup measured at one layer and quoted at another is exactly the overgeneralization that benchmarking discipline warns about [28]; the five phases of this study are designed to make each layer's contribution visible instead of collapsing them into one number.

This article presents a multi-boundary evaluation of an on-demand JSON parser on a real Node.js server workload. The evaluation is organized into five boundary phases: (A) full materialization, (B) partial projection, (C) deep selective access, (D) repository-level access over a state store, and (E) a complete HTTP endpoint. The treatment engine is a C++23 on-demand JSON parser exposed through a WebAssembly 64-bit binding; the baseline is the V8 JSON.parse path of the same application. Every cell is measured on two sites — the author's development device and the workload's production-like server — over 15 paired rounds, with a locked round-level estimand and paired bootstrap inference. The contributions are: (i) boundary-resolved evidence of where the wasm path wins, ties, or loses against V8 on a real workload; (ii) a locked statistical protocol, recomputed from archived per-round exhibits rather than copied from intermediate reports; and (iii) a checksum-proven measurement pipeline — corpus manifest, harnesses, raw exhibits, and schema-validated records — sufficient for independent reanalysis. The scope is deliberately latency-centered: the protocol measures wall-clock time at five boundaries and does not measure memory, CPU time, or energy, and the treatment path is the wasm64 binding rather than a native in-process build; both restrictions are revisited when we discuss threats to validity.

We ask three questions. RQ1: How does the JSON access pattern — full materialization, partial projection, or selective traversal — affect the relative performance of the two parsers (phases A–C)? RQ2: Does an on-demand advantage appear at the repository boundary of a real state-store workload (phase D)? RQ3: To what extent does the repository-level difference persist in the end-to-end latency of `GET /rekap` (phase E)? The remainder of the article describes the systems, protocol, and inference procedure (Materials and Methods), reports the results per boundary (Results and Discussion), and closes with limitations and conclusions.

# MATERIALS AND METHODS

## Study Systems

The treatment system is ze_json, a header-first on-demand JSON parser written in C++23; its design follows the on-demand parsing interface in which reading looks like a DOM walk while the implementation only materializes what is read [2]. Its core avoids the C++ standard library, and its document interface is lazy: a Document opens the raw bytes, a Value walks to the requested position, and array or object iteration is a stateless cursor over the input rather than a materialized container. The parser is compiled to 64-bit WebAssembly (wasm64) and loaded into Node.js through a minimal C-ABI binding that exposes two classes, ZeDocument and ZeParser, together with the library's structural-scanner exports. The binding enables the library's default byte-level scanner (scanner8); alternative vectorized scanners measured slower in this configuration during development and are not enabled. Internally, materialized values are allocated from an arena, and per-document parser state lives in a fixed pool of slots behind the C ABI, so calls carry small integer handles rather than serialized payloads. The wasm64 target provides the parser with a 64-bit linear address space for its arena; this is a design property of the binding, not a measured memory result. The parser's UTF-8 validation and number-parsing lookup tables are generated from published algorithms [14, 15]. Throughout the article, this configuration is referred to as the C++23 on-demand JSON parser exposed through a WebAssembly 64-bit binding.

The baseline system is saq-report, the Node.js/Express application of the SAQ reporting server — the workload whose JSON paths motivate this study. Its state store keeps six domains (assistants, courses, lecturers, schedules, reports, and globalConfig) as JSON documents. Two repository implementations matter here. The file-store repository reads pretty-printed (indent-2) JSON from disk and supports element counting through read().length, paying one eager JSON.parse per read. The Mongo-backed repository keeps cached canonical bytes and serves count-style requests through readCount(), a path that pairs naturally with an on-demand parser because no materialization is required. The application also exposes GET /rekap, whose handler reads four repositories, renders an EJS template, and returns a 47,888-byte response. A JSON.stringify-based export service exists in the code base but lies outside the measured paths.

All experiments use the saq_payload_v1 corpus: six anonymized, store-shaped documents (360 to 39,209 bytes; 88,381 bytes in total; Table 1), generated deterministically (seed 20261108) to mirror the real stores' document shapes and pretty-printing, with per-document SHA-256 provenance in the corpus manifest. Anonymization replaced personal content while preserving document structure, and regeneration with the same seed is byte-identical, which makes the corpus itself reproducible evidence. The corpus is fixed across all phases, sites, and runs as the generated/anonymized reference; the dev endpoint used a mirror of these files, whereas the server endpoint read a local MongoDB store whose seed files were recorded only as provenance, so cross-site content identity is not claimed. Its six documents also cover both root shapes the stores produce — wrapped objects with a single top-level key and bare array or object roots — so the parser interfaces are exercised on the shapes the application actually serves.

## Boundaries and Engine Pairing

Figure 1 shows the five measured boundaries. Phase A parses each full document on both engines (baseline: JSON.parse; treatment: the on-demand parser's full-document path). Phase B projects a partial shape out of each document (baseline: JSON.parse followed by a projection in JavaScript; treatment: an L2 projection over the lazy document). Phase C performs deep selective access to fields inside nested structures (baseline: parse-then-select; treatment: L1 traversal with the lazy cursor). Phase D sits at the repository layer: the baseline path reads the document and counts elements via read().length, while the treatment path serves the count from cached canonical bytes via readCount(); the two store backends — the warmed Mongo cache and the file store — are measured separately. Phase E spans the complete HTTP endpoint: two instances of the same server, one bound to the V8 baseline path and one to the on-demand path, serve identical sequential traffic to GET /rekap.

Engine pairing follows one rule: both engines must produce identical observable outputs. Phases A–C compare like-for-like access results on the same corpus documents, and phase E enforces a byte-parity gate across all 300 response bodies (Measurement Protocol). Phase D is the one boundary where the treatment path differs structurally, because the canonical-bytes count design replaces eager parsing. We therefore treat phase D as a repository-design comparison that includes the parser, not a parser-only comparison — a distinction carried through all claims.

Four additional supporting runs, executed with an earlier core version (0.3.1), replicate phases A–D on the dev device and are used only as corroboration. All primary runs loaded the same WebAssembly artifact (SHA-256 beginning 9795f2e8) on both sites. The first dev phase-E run predated a final commit change in the workload pairing and was re-run after the change; both runs are reported separately and never pooled.

## Measurement Protocol

Figure 2 summarizes the protocol shared by all phases. Each phase run executes three untimed warmup iterations per path, then 15 independent measured rounds. The order of paths is rotated every round (a round-robin offset) to cancel systematic order effects, and in phase E the engines alternate which instance starts each round. A round's value is the mean of its within-round repetitions; repetition counts adapt to document size (30 for small documents, 5 for large ones, and 2 at the repository phase). No measurement is trimmed: every per-round value is stored raw in the exhibit. Three protocol choices deserve justification. Warmup exists because the first executions of a path pay one-time costs — bytecode compilation, inline-cache warming, allocator growth — that would otherwise be charged to the earliest rounds. Rotation of path order exists because a fixed order lets thermal, scheduler, or cache-carryover effects systematically favor whichever path runs second; rotating the offset each round turns such effects into noise that both paths experience. Reporting every untrimmed round is what allows the inference step to resample rounds honestly instead of trusting a pre-digested summary.

%%FIGURE|article/scripts/Grapher/diagram/fig2-measurement-protocol.png|Figure 2. Measurement and provenance pipeline shared by all phases: warmup, 15 measured rounds with rotated path order, per-round aggregation, the phase-E parity gate, raw exhibits, schema-validated records, and the derived evidence ledger. (Figure produced with AI assistance; see Declaration of AI use.)

Phase E has its own protocol because the measured unit is a request. Each of the 15 rounds issues 20 requests in total — 10 to each engine instance, issued strictly sequentially, with engines alternating by position — so each engine receives 150 requests per run. Three untimed warmup requests per engine precede measurement. A parity gate then checks that all 300 response bodies are byte-identical (one SHA-256 hash per run); a mismatch voids the run. Per-request latency and the body hash are recorded for every request. The alternation pattern deserves a note: because engines alternate by request position within a round and swap the starting engine between rounds, neither engine systematically enjoys the warmer cache or the quieter machine window; any residual asymmetry appears in the round-level pairing that the bootstrap resamples.

Every run writes a raw exhibit (the per-round and per-request measurements as JSON) and a measurement record in a versioned schema carrying the run identifier, site, host, library versions, Git commits, corpus identity, configuration, and results. A schema validator must accept a record before it enters analysis; all 11 primary records pass. Run identifiers encode the host, a timestamp, and the root repository's commit hash. One phase-E pilot run with a different request budget (2 rounds of 3 requests) was excluded before any analysis.

## Statistical Inference

Figure 3 shows the inference procedure. For each cell — a (phase, site, document or store, run) combination — the per-round engine times T_V8,i and T_ZE,i for i = 1..15 yield the primary estimand S = T_V8/T_ZE, computed as the ratio of round-level medians, θ = median(T_V8,i)/median(T_ZE,i). This is a ratio of across-round medians, not the median of fifteen paired-round ratios. Values above 1 mean V8 took longer and therefore favor the on-demand path; values below 1 mean the on-demand path took longer and favor the V8 baseline. Within a round, phases A–D use the harness-stored mean of repetitions, and phase E uses the median of the 10 per-engine requests — an analysis choice stated explicitly because request-level latencies are heavy-tailed.

%%FIGURE|article/scripts/Grapher/diagram/fig3-decision-flow.png|Figure 3. Inference procedure per cell: round-level medians form the point estimate S = T_V8/T_ZE; joint resampling of the 15 paired rounds (B = 10,000, fixed seed) yields a 95% percentile confidence interval whose position relative to 1 carries the inferential statement; claims remain per-boundary. (Figure produced with AI assistance; see Declaration of AI use.)

Uncertainty comes from a paired round-level bootstrap: the 15 (V8, ZE) round pairs are resampled jointly, the ratio of medians is recomputed in every replicate, and the 2.5th and 97.5th percentiles of B = 10,000 replicates (fixed seed 20261117) form the 95% confidence interval. A bias-corrected and accelerated (BCa) variant is computed from the same resamples with log-scale jackknife acceleration as a sensitivity analysis with the same seed and resample count; its intervals are archived with the derived statistics and do not replace the percentile interval. Tables report four decimals; the narrative rounds to two.

We interpret intervals, not accept/reject decisions: an interval entirely above 1 indicates an on-demand advantage at that boundary, run, and site; entirely below 1 indicates a V8 advantage; an interval containing 1 indicates that the advantage is not distinguishable at this design's precision — never a null-hypothesis verdict. We report confidence intervals rather than significance tests [28]. Because the harness also emits a descriptive pooled-request median ratio (all requests of both engines pooled within a run), that legacy convention is reported exactly once, as a table note directly under Table 7; it is descriptive and is not the target of the reported confidence interval. Every inferential claim is tied to the round-level ratio of medians, not to the pooled request ratio.

## Sites and Reproducibility

Two sites are measured. The dev device is an AMD Ryzen 5 5500U (12 threads, 7.4 GB RAM, Windows 10.0.26200); the server is an Intel Core i5-9400 at 2.90 GHz (6 cores, 7.9 GB RAM, Windows 10.0.26300) — the machine class on which the workload normally runs. Both sites run Node 26.13.1 with V8 14.6.202.34-node.40 and load the same wasm64 artifact (SHA-256 beginning 9795f2e8; ABI 2026000302; core 0.3.2, binding 0.3.0). Phases A–D bind the workload at commit 8c7f2d4; phase E binds 534d9a8, while the first dev phase-E run used the earlier pairing 501cc03 and was re-run on the final pairing.

Two integrity mechanisms bound the interpretation. The schema validator rejects records that lack required provenance fields — including the rationale that documents what each measurement was for — so every number in this article traces to a machine-checked record rather than to a manual transcription. And because run identifiers embed the root commit hash, any accidental mixing of tree states across runs would be visible in Table 2 instead of silent.

Everything required to reproduce the numbers is archived with checksums: the corpus and its per-document manifest, the harness scripts, the raw exhibits, the schema-validated records, and a derived evidence ledger that lists every point estimate and interval used in this article with its SHA-256 provenance (see Data and Supplementary Materials). Supporting runs with core version 0.3.1 reproduce the A–D per-document ordering and the repository shape on the dev device; they do not cover the endpoint boundary. The protocol deliberately excludes memory, CPU-time, and energy measurements and any cold-start cache behavior; these omissions are revisited under Threats to Validity.

# RESULTS AND DISCUSSION

## Access-Pattern Boundaries (Phases A–C)

Phase A pays the eager strategy's full price on the baseline, and the on-demand path pays more still. Every phase-A ratio lies far below 1 (Table 3; Figure 4): on the dev device S ranges from 0.0428 (lecturers) to 0.0613 (reports), and on the server from 0.0493 (courses) to 0.0669 (assistants). Because S = T_V8/T_ZE, these values mean that V8's full parse plus materialization took roughly 15–23× less time than the on-demand parser's full-document path; the reciprocal of each point estimate lies between 15.0 and 23.3 over the twelve cells. All twelve intervals lie entirely below 1, making V8's full-materialization advantage the least boundary-sensitive result in the study. The phase-A ratios are also the cleanest read of the underlying engines: with the access pattern held at its maximum — the whole document — the comparison isolates the materialization strategy plus engine call overhead, and here the on-demand path — which makes more, smaller calls across the binding — loses to the engine's built-in parser; crossing cost is a plausible explanation but was not isolated by this protocol. The dev and server intervals overlap for every document (for example, courses 0.0494 [0.0385, 0.0631] versus 0.0493 [0.0426, 0.0549]), so the site dimension does not reorder this boundary. Practically, this boundary is a ceiling for the wasm path: an application that reads every field of every document cannot win by reading less, and in this configuration it does not win on full materialization itself either.

Phase B asks whether the gap narrows when the baseline is allowed to project a partial shape after parsing. It narrows but does not close: the on-demand projection path is 6–13× slower than V8 across all cells (S = 0.08–0.16; Table 4), so the baseline's parse-then-project route remains the cheaper of the two. Every interval remains entirely below 1 (largest upper bound 0.1716). Projection roughly halves the disadvantage relative to phase A — the ratio grows by a factor of two to three — but the on-demand path never catches up. The uniformity across sites — the largest cross-site difference between point estimates at this boundary is about 0.016 — supports reading phase B as a property of the access pattern rather than of either machine.

Phase C is where the comparison stops favoring V8 uniformly. Under deep selective access the two engines trade places depending on the payload (Table 5). V8 is clearly faster on the reports array (S = 0.29 [0.24, 0.32] dev; 0.31 [0.26, 0.33] server) and on the tiny globalConfig object (S = 0.05 [0.04, 0.06] on both sites), where the on-demand path's cursor setup dominates. The comparison is not distinguishable on courses (0.92 [0.75, 1.12] dev; 0.86 [0.75, 1.04] server) and on dev lecturers (1.05 [0.87, 1.13]), while at the server lecturers the interval slips entirely below 1 (0.96 [0.91, 0.98]), favoring V8. The on-demand path is faster on schedules (1.65 [1.51, 1.97] dev; 1.50 [1.09, 1.56] server) and on assistants at the server (1.42 [1.23, 1.45]), with the dev assistants interval still containing 1 (1.17 [0.93, 1.24]).

The crossover is consistent with a cost-model reading: in phase C the baseline pays one full parse and then accesses fields cheaply, while the on-demand path avoids the parse but pays cursor navigation for every accessed position. Payloads for which the full parse is very cheap relative to navigation — the 360-byte global object — or for which the access touches enough of the document that the eager parse amortizes — the reports array — leave the on-demand path behind; on the larger schedules and assistants documents the cursor path can win when the accessed fraction is small. We report this reading as a consistent interpretation rather than a proven mechanism, because the protocol does not instrument per-field access counts. The cross-site picture reinforces the payload dependence: the two sites agree in direction on reports, globalConfig, courses, and schedules, and disagree only in whether assistants and lecturers tip past the distinguishability threshold — assistants clearly on-demand-favored at the server but not at the dev device, lecturers V8-favored at the server but not at the dev device. Boundary C is therefore best summarized as a crossover region rather than a win or a loss for either engine. The four supporting runs (core 0.3.1) reproduce the per-document ordering on the dev device and are archived alongside the primary ones.

## Repository Boundary (Phase D)

Phase D measures the repository layer of the real workload. The warmed Mongo canonical-bytes path is 2.88 [2.57, 3.05] times faster on the dev device and 2.67 [2.51, 2.86] on the server — the largest advantage in favor of the on-demand configuration measured in this study, limited to the warmed Mongo canonical-bytes path (Figure 5; Table 6), with both intervals entirely above 1. The file-store path, in contrast, shows no advantage: 0.95 [0.77, 1.11] on the dev device and 0.99 [0.97, 1.04] on the server, both intervals containing 1. This negative result is reported as it stands: over the file store, serving counts through the on-demand parser does not beat the eager path.

## Discussion

Access pattern is the first-order variable, but not in the direction anticipated at the outset. The on-demand configuration's disadvantage is largest when the workload reads every field and shrinks as the access pattern becomes more selective: V8 is 15–23× faster at full parse (phase A), 6–13× faster under projection (phase B), and the comparison becomes payload-dependent, from S = 0.05 (V8 faster) to S = 1.65 (on-demand faster), under deep selective access (phase C). This ordering reproduces on both sites with intervals that agree in direction, which makes it the most portable conclusion of the study (RQ1).

At the repository boundary, the design of the store dominates the parser question (RQ2). The warmed canonical-bytes path wins by 2.7–2.9× on both sites, but that number belongs to the combination of caching, canonical bytes, and lazy counting — not to the parser alone — and the same parser over the file store wins nothing. For practitioners the implication is concrete: on-demand parsing pays where the application can avoid re-parsing cached bytes, not merely from swapping the parser under an unchanged, I/O-bound design.

At the endpoint the advantage compresses to 1.03–1.15 across sites and runs (RQ3). The endpoint adds middleware, routing, four repository reads, template rendering, and HTTP serialization on top of the parsing path — work that no parsing strategy can amortize. The server site shows a distinguishable 1.15; the dev device does not. Whether a 1.15x endpoint speedup on the server (about 13% lower latency) justifies the binding complexity is a deployment decision; what this study adds is the boundary-resolved accounting that supports such a decision. For engineering practice the evaluation suggests a sequence: first measure the access pattern, because phase-A-style full reads overstate what an application actually needs; then check whether the store can serve canonical bytes instead of re-parsing, the phase-D lever worth 2.7–2.9× when applicable; and only then set endpoint expectations from endpoint measurements, because the fixed cost of the HTTP path bounds any parsing gain.

The delivery mechanism is a plausible contributor to the boundary pattern, but it was not isolated. Crossing the JavaScript/WebAssembly boundary entails parameter marshalling and a runtime switch, and the on-demand contract turns one large parse call into many small access calls; the scanner and parser exports are intended to keep those crossings small. In phase D the workload replaces repeated crossings with a single canonical-bytes count, which is consistent with the 2.7–2.9× gain, whereas at the endpoint those crossings are amortized across non-parsing work. Because crossing counts and marshalling time were not measured as a separate factor, this reading is an interpretation rather than an established mechanism. Native in-process delivery would avoid the boundary crossing but sacrifices the portability and sandboxing that make the wasm route attractive for Node.js servers [23, 25].

Runtime context is labeled explicitly. All results above come from Node 26.13.1 with V8 14.6. An earlier round of the project's own measurements on Node 24 with V8 13.6 reported a larger repository-level advantage — about 2.85× on the dev device and 1.30× on the server. Those numbers are mentioned only as labeled, non-comparable history: a different runtime, different commits, and a corpus iteration in between. None of them enters the evidence above, and no cross-runtime pooling is performed. The distinction between evidence and narrative matters: every number that carries a conclusion in this article was produced under one runtime generation, one artifact hash, and one workload pairing per phase, and remains comparable only within those labels. Readers comparing against other Node release lines should expect the boundary pattern — strongly V8-favoring at the full-access boundaries, design-dependent at the repository, and compressed at the endpoint — to be more stable than the specific magnitudes.

### Comparison with Prior Results

The full-materialization result runs opposite to the on-demand advantages reported for native parsers against eager DOM-style parsing [2, 3]: in this wasm64 configuration the observed disadvantage is consistent with the combined effect of binding calls and V8's optimized built-in parser when the whole document is consumed; the protocol does not isolate those contributions. The narrowing under projection and the crossover under traversal are consistent with the trade-offs reported by the selective-access literature itself [4, 6, 9]. The endpoint-level compression is the least documented part of this pipeline, precisely because most evaluations stop before the HTTP stack; the nearest analogue is the execution-environment literature for WebAssembly [23, 26], which likewise reports environment-dependent deviations from native-style performance. The present study complements that literature with a boundary-resolved, paired design on a concrete workload [28].

### Threats to Validity

Internal validity: each cell rests on one run of 15 paired rounds (two runs only for phase E on the dev device). The paired design, path-order rotation, and warmup address order and start-up effects, but unmodeled background load can still shift an individual cell; the fixed bootstrap seed makes the resampling reproducible and does not control measurement effects. Construct validity: phase D measures a repository design rather than a parser, and phase E includes non-parsing latency by design; both are labeled as such. The protocol does not measure memory, CPU time, or energy, although the motivation for on-demand parsing includes allocation savings; cold-cache Mongo behavior — building the canonical cache — is likewise unmeasured. External validity: two sites, one workload family, one corpus shape, Windows hosts, and a wasm64-only treatment (no native-in-process comparator at the repository or endpoint boundaries) limit generalization. Statistical validity: bootstrap intervals at 15 rounds are honest but wide; cells whose interval contains 1 are reported as not distinguishable, never as equality. Round-level medians also damp the heavy-tailed request noise that a pooled analysis would smear into a single number; that robustness, rather than statistical power, is the reason the design pairs at the round level. Finally, aggregate hypotheses about parser latency, throughput, and memory consumption cannot be decided from these boundaries; the article reports per-boundary latency evidence only. # CONCLUSION

This study set out to locate where an on-demand JSON parser can beat V8 on a real Node.js server, and the answer is boundary-resolved. Under full materialization V8 is 15–23× faster (S = 0.04–0.07; phase A). Under partial projection V8 remains 6–13× faster (S = 0.08–0.16; phase B). Under deep selective access the comparison becomes payload-dependent, from S = 0.05 on tiny objects (V8 faster) to S = 1.65 on the densest payload (on-demand faster) (phase C). At the repository boundary the warmed canonical-bytes path is 2.88× (dev device) and 2.67× (server) faster for the on-demand configuration, while the file-store path shows no advantage — a negative result reported in full (phase D). At the HTTP endpoint the advantage is not distinguishable on the dev device (1.05 and 1.03) and is modest but distinguishable on the server (1.15) (phase E).

Methodologically, the study contributes a locked round-level estimand with paired bootstrap inference, recomputed from archived exhibits; a byte-parity gate that keeps engine comparisons output-identical; and a checksum-proven pipeline from corpus to evidence ledger. The practical reading for Node.js practitioners is that on-demand parsing through WebAssembly is most valuable where the store design lets lazy counting replace re-parsing and where selective traversal touches few fields of a large document; full-materialization boundaries favor V8 in this configuration, it is not a uniform win at every layer, and endpoint-level expectations should be set by endpoint-level measurements. None of the boundary verdicts required pooling across sites, runs, or estimands: every number stands on its own 15 paired rounds. The five-phase structure, the parity gates, and the archived exhibits are reusable beyond this workload: any Node.js server that stores JSON can be instrumented the same way, and the claim-boundary matrix of Table 8 transfers as a reporting checklist.

Future work follows the omissions of the present protocol: cold-path repository measurements that build the canonical cache, memory and CPU-time accounting alongside latency, a native-in-process comparator at the repository and endpoint boundaries, additional endpoints and payload shapes, and repeated runs per cell to tighten the intervals.
